\chapter{Federación con capas personalizadas y salidas heterogéneas (FedPerH)} \label{cap3}

\vspace*{5mm}

En esta sección vamos a proponer una solución al problema de clasificación multi-etiqueta en entornos federados. Explicaremos la arquitectura que se va a usar para el algoritmo, la base del mismo y las modificaciones que hemos realizado.

\section{Arquitectura de la solución}

Tendremos N clientes y cada uno realizará una tarea de clasificación con un conjunto de etiquetas diferente. Estos clientes quieren realizar el entrenamiento del modelo que usarán para realizar la tarea de manera cooperativa pero sin compartir los datos. Para que realicen esta tarea vamos a usar modelos personalizados que contarán con una parte común que es la que se compartirá con el servidor y un conjunto de capas personalizadas que quedarán en los clientes. De esta manera parte del modelo tendrá una función general y compartida entre los demás nodos y cada uno de ellos entrenará la parte específica a su tarea de manera local. 

El servidor crea el modelo compartido y lo envía a cada uno de los clientes, estos añaden las capas personalizadas para completarlo en las que se incluye la salida del modelo según el número de etiquetas que tengan los datos para ese cliente. Los clientes una vez tienen el modelo completo realizan varias épocas de entrenamiento local, guardan el estado del modelo, separan la parte común y las capas personalizadas. El estado actualizado de las capas personalizadas se almacena en el cliente mientras que la parte común se devuelve al servidor. El servidor recibe la parte común de todos los clientes las cuales tendrán un estado distinto para cada uno ya que se han entrenado con datos diferentes y las agrega asignando un peso a cada modelo según el número de datos de entrenamiento. Como resultado de esta agregación obtenemos un modelo común actualizado que se enviará a cada uno de los clientes para volver a iniciar el proceso hasta que se realicen un número determinado de rondas o hasta que el modelo converja.

En otros sistemas federados es común que el modelo se comparta al completo con el servidor ya que el entrenamiento de las capas de salida es relevante para todos los clientes. En nuestro caso esto no se cumple ya que la activación de la salida es única para cada cliente y la posición de la etiqueta ``agua'' en un cliente correspondería a un objeto distinto en otro. Por ello el modelo que compartimos con el servidor está truncado y no serviría para usarse ya que no tiene una capa de salida que se ajuste a los datos de los clientes.



\section{FedPer}

El aprendizaje federado necesita una insfraestructura que permita mover modelos de un lado a otro entre el servidor y los clientes, ejecutar el entrenamiento con los datos locales y agregar los modelos actualizados. Para evitar la implementación de todo el sistema desde cero vamos a usar de base el entorno de trabajo para aprendizaje federado Flower \footnote{\url{https://flower.ai/}} que nos provee de esta infraestructura. Más en concreto haremos uso del baseline de Flower FedPer \footnote{\url{https://flower.ai/docs/baselines/fedper.html}}, una implementación de ~\cite{Manoj:FedPer} el cual propone una aplicación del método de \textit{Backbone Sharing} que vimos en ~\cite{Ye:HFL_Survey}. FedPer es un entorno simulado que crea el servidor y los clientes, en el servidor se instancia el modelo global con dos partes diferenciadas llamadas \textit{cuerpo} y \textit{cabeceras}: el \textit{cuerpo} corresponde a la parte del modelo que va a ser compartida y las \textit{cabeceras} son las capas que van a ser entrenadas en el cliente pero no van a devolverse. El servidor inicializa el \textit{cuerpo} y se envía a cada uno de los clientes los cuales actualizan sus modelos locales con él. Cada modelo local se entrena con sus datos y los \textit{cuerpos} actualizados se devuelven al servidor el cuál realiza la operación de agregación, que en nuestro caso será FedAvg ~\cite{mcmahan2023communicationefficientlearningdeepnetworks}, pero solo con la parte del modelo enviada por los clientes. Una vez actualizado el modelo global se devuelve a los clientes para la siguiente ronda de entrenamiento Figura \ref{fig:personalized_layers}.

\section{Modelo}

Para las capas compartidas con el servidor necesitamos un modelo que nos ayude con la tarea de procesamiento de imágenes. Las redes convolucionales ~\cite{10.3389/fncom.2023.1153572} son ideales para en tratamiento de imágenes ya que son capaces de realizar operaciones sobre las matrices de datos multi-dimensionales que la conforman, cuantas más capas tengan mejor será el rendimiento, sin embargo si son muy profundas aparece el problema del desvanecimiento del gradiente. Al entrenar estas redes la función de \textit{backpropagation} envía una señal de error desde la salida hacia la entrada de la red para ajustar los pesos, si la red tiene muchas capas este error se va multiplicando por números cada vez más pequeños hasta que las primeras capas apenas se ajustan lo que no les permite aprender. En ~\cite{he2015deepresiduallearningimage} se propone la red ResNet la cual resuelve el problema del desvanecimiento del gradiente mediante capas residuales. Estas capas funcionan de manera que la salida se calcula en base a la entrada por lo que la transformación que realiza la capa se convierte en un problema de optimización el cuál es mucho más sencillo de realizar puesto que la corrección es menor. Estas capas residuales permiten que podamos tener redes más profundas y han sido usadas en problemas de tratamiento de imágenes como AlphaGo ~\cite{alphago} y AlphaFold ~\cite{alphafold}. Nosotros vamos a usar ResNet34 la cuál tiene 34 capas residuales que se encargará de de las funciones comunes a las diferentes tareas. Aunque nosotros usemos ResNet34 para la base de nuestro modelo la arquitectura es independiente de éste por lo que se podría usar otra red.

Las capas personalizadas de cada cliente se encargarán de la parte específica. Para las capas personalizadas vamos a añadir para cada servidor dos capas convolucionales y una capa linear para la salida con un nodo para cada etiqueta.

\section{Modificaciones}

FedPer está adaptado para la implementación de un sistema que realiza una clasificación de imágenes multi-clase. Las modificaciones que debemos realizar son para que este mismo sistema sea capaz de clasificar imágenes multi-etiqueta.

La primera modificación es en referencia a los datos. FedPer asume que cada uno de los clientes entrena imágenes con una serie de etiquetas distintas que se eligen de manera aleatoria entre todas las del conjunto pero la salida de todas las capas personalizadas de los clientes tienen de dimensión el número de etiquetas totales del conjunto de datos. Nuestro caso es diferente al reducir la dimensión de la salida de las capas personalizadas únicamente al número de etiquetas del conjunto de datos de cada cliente. Por tanto debemos realizar un tratamiento previo al conjunto de datos multi-etiqueta que vamos a usar para prepararlo para esta tarea. Primero realizamos una selección de las etiquetas que tendrá cada conjunto y nos aseguramos que no están presente en el resto. Luego debemos actualizar los índices de las etiquetas en cada conjunto para que tomen valores entre 0 y n siendo n el número de etiquetas menos uno en las imágenes de ese cliente. Esto debemos hacerlo para que la salida nos de siempre un vector de dimensión n.

La segunda modificación tiene que ver con las capas personalizadas. En FedPer las capas personalizadas no se comparten desde los clientes al servidor pero es este el que las inicializa con los mismos pesos para todos los clientes. En nuestro caso vamos a dejar que cada cliente inicialice sus capas personalizadas con pesos distintos y el servidor solamente inicializará la parte común del modelo.

La tercera modificación se relaciona con el entrenamiento y más concretamente con la función de pérdida. FedPer usa \textit{CrossEntrophyLoss} para el entrenamiento multi-clase. En nuestro caso el modelo como salida nos da un vector de dimensión n con valores entre menos infinito e infinito o \textit{logits}. La función \textit{BCEWithLogits} nos permite aplicar la función \textit{Binary Cross Entropy} que evalúa cada clase de manera independiente junto con la \textit{sigmoid} para poder trabajar con esos \textit{logits}.

Por último hemos adaptado la evaluación del modelo, que al ser imágenes multi-clase solamente debía tener una clase activa para cada ejemplo y por ello comprobaba que la predicción y la salida real fueran idénticas. En nuestro caso debemos introducir técnicas de evaluación para clasificación multi-etiqueta la cuál conlleva ciertas dificultades en las que entraremos más en profundidad en la siguiente sección.
